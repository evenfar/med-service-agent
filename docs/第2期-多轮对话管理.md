# 第2期 · 多轮对话管理

> 会话存得稳（原子写 + 损坏降级）、历史压得对（工具事实进摘要、切点避开 tool 消息）、上下文不再无限膨胀。

## 本期目标

- 掌握 `app/agent/storage.py` 的原子写（`.tmp` + `os.replace`）与损坏/版本不符时降级为新会话。
- 理解 `app/agent/summarizer.py` 的 `render_transcript`：为什么 tool_calls 与工具结果必须进摘要。
- 理解按条数阈值压缩（`history_threshold=12` / `history_keep_recent=4`）是教学简化，生产应按 token 预算。
- 吃透 `app/agent/base.py` 的 `compress_history`：切点为什么不能落在 tool 消息中间。

## 架构与数据流

```text
finish_turn()（app/agent/base.py，每轮回复后）
   │ 1) 追加 assistant(JSON) 到 raw_messages
   │ 2) memory_manager.update_short_term(最近6条)
   │ 3) maybe_compress()   4) save()
   ▼
len(raw_messages) > history_threshold(12) ？ ──否──▶ 直接 save_session()
   │ 是
   ▼
compress_history()（app/agent/base.py）
   split = len(raw_messages) - history_keep_recent(4)
   while split > 0 且 raw_messages[split].role == "tool": split -= 1   ← 切点避开 tool
   old, recent = raw_messages[:split], raw_messages[split:]
   summary = summarize(client, old, prev_summary=self.summary)   ← 增量摘要
   │
   ▼
summarize()（app/agent/summarizer.py）
   render_transcript(old)：user/assistant/tool_calls/tool 全渲染（工具结果截断200字）
   SUMMARY_PROMPT.format(prev_summary, transcript)（app/prompts/summarizer.py）
   client.chat(..., temperature=0.3, purpose="summarize")
   │
   ▼
save_session()（app/agent/storage.py）
   写 path + ".tmp" ──▶ os.replace(tmp, path)   原子替换，崩溃不留半截文件

下一轮 render_messages()（app/agent/base.py）：
   [system] + [记忆区] + [system: 此前对话摘要] + raw_messages(只剩 recent)
```

## 核心实现讲解

### `app/agent/storage.py`：原子写与损坏降级

- `save_session(path, messages, summary, short_term_memory=None)` 组装 payload：`version`（`SESSION_VERSION = 1`）、`updated_at`、`summary`、`messages`、`short_term_memory`。先 `os.makedirs(..., exist_ok=True)`，写入 `path + ".tmp"`，然后 `os.replace(tmp, path)`。**同文件系统上 replace 是原子操作**：进程在写中途崩溃，目标文件要么还是旧内容、要么已是完整新内容，绝不会是半截 JSON；残留的最多是 `.tmp`（`test_no_tmp_left_after_save` 验证正常路径下连 `.tmp` 都不剩）。
- `.tmp` 故意放在目标文件**同目录**（`path + ".tmp"` 而非系统临时目录）：`os.replace` 的原子性只在同一文件系统内成立，跨盘 rename 会退化成"复制+删除"，中途崩溃照样丢数据。
- `load_session` 的三级降级全部返回 `None`：文件不存在；`json.JSONDecodeError` / `OSError`（损坏或读失败）；`version != SESSION_VERSION` 或 `messages` 不是 list。调用方（`BaseAgentRuntime.__init__`）拿 `None` 就当全新会话——**用户体验优先于报错**：聊天记录坏了不应该让用户面对栈回溯。版本检查为将来格式演进留路：老文件直接视为新会话，不会用旧结构误恢复。
- `delete_session` 吞掉 `FileNotFoundError`，幂等——`reset_session` 连点两次不炸（`test_delete`）。
- 会话文件里只存 user/assistant/tool 原始消息，system 与摘要注入发生在 `render_messages`，不在磁盘里冗余。`short_term_memory` 随会话一起持久化：`BaseAgentRuntime.save()` 传入 `memory_manager.stm_to_dict()`，恢复时经 `_restore_extra` 钩子由 `MedicalAgent` 调 `memory_manager.restore_stm(...)` 还原——压缩丢掉的细节，部分由短期记忆补回。

### `app/prompts/summarizer.py`：摘要要保什么

- `SUMMARY_PROMPT` 是一个带两个占位符的模板：`{prev_summary}`（上一次的摘要，增量合并的锚点）与 `{transcript}`（本次待压缩的渲染文本）。
- 开头直接给硬指标——"不超过 300 字"，并列举**必须保留的三类信息**：症状/持续时间/既往检查结论；已查过的预约单号/报告单号/药品名；已给出的重要建议与未回答的追问。压缩最容易丢的不是寒暄，而是这些"事实锚点"——丢一个单号，下一轮就要重新问用户。
- 结尾一句"只输出摘要正文"同样是约束：不要让摘要本身再套一层"好的，以下是摘要："的废话或 markdown 标题，它要被原样塞进 system 消息。

### `app/agent/summarizer.py`：工具事实必须进摘要

- `render_transcript(messages, max_tool_chars=200)` 三类消息三套渲染：user → `用户：…`；assistant → `助手：正文 [调用工具 名称(参数)]…`（tool_calls 全部列出）；tool → `工具结果：…`（**截断到 200 字**，工具返回的 JSON 可能很长，摘要原料不需要全文）。
- 为什么 tool_calls / tool 结果必须渲染：多轮里"已查过的预约单号、报告单号、药品名、相互作用结论"是后续轮次的关键事实。丢掉它们，模型下一轮会重复调用工具，甚至凭记忆编造上次查询结果。`SUMMARY_PROMPT`（`app/prompts/summarizer.py`）把这一点写成硬要求：必须保留症状与持续时间、已查过的单号/药品、已给建议与未答追问，不超过 300 字，"只输出摘要正文"。
- `summarize(client, old_messages, prev_summary)` 是**增量式**：新摘要由"上一次摘要 + 本次 transcript"共同生成，压缩过的信息滚雪球式延续；`temperature=0.3` 偏低温求稳。参数是 `BaseLLMClient` 抽象而非 openai 客户端，所以 `MockLLMClient` 也能跑（`test_summarize_via_mock` 断言输出以"（摘要）"开头），摘要链路同样被离线测试覆盖。

### `app/agent/base.py`：阈值触发与压缩切点

- `maybe_compress`：`len(self.raw_messages) > self.settings.history_threshold`（默认 12）才压缩；`finish_turn` 在**回合结束**调用它，而不是回合中间——ReAct 循环里 assistant(tool_calls) 与 tool 消息必须连续，回合中动历史容易破坏协议。
- `compress_history` 的三步：
  1. `split = len(self.raw_messages) - self.settings.history_keep_recent`（默认保留最近 4 条）；
  2. `while split > 0 and self.raw_messages[split].get("role") == "tool": split -= 1`——**切点不能落在 tool 消息中间**。OpenAI 协议要求每条 tool 消息紧跟在携带对应 tool_calls 的 assistant 消息之后；从 tool 前面切开会让 recent 段以孤儿 tool 消息开头，真实接口直接 400。回退到非 tool 消息（通常是 assistant 或 user）再切，协议完整；
  3. `old, recent = messages[:split], messages[split:]`，`self.summary = summarize(self.client, old, self.summary)`，`self.raw_messages = recent`，打印压缩提示。
- 摘要的回注位置在 `render_messages`：作为一条 **system** 消息（"此前对话摘要：…"）插在记忆区之后、raw_messages 之前——它是系统上下文而非用户发言，不应污染 user/assistant 交替结构。
- 消息顺序本身有语义：system（身份与规则）→ 记忆区（长期档案/技能目录）→ 摘要（历史压缩）→ 最近对话。越靠前的越"稳定"，越靠后的越"新鲜"；摘要放在原始消息前面，模型能把它当作背景而非指令。`history_size` 属性让 CLI（`main.py` 的"已恢复上次会话（N 条历史）"）与测试都能直接观察会话规模。

### 简化的坦白：条数阈值 vs token 预算

`history_threshold` 按消息**条数**触发，这是教学简化（`app/config/settings.py` 注释里明说"生产应按 token 预算，见 docs 第2期"）。缺陷很直接：一条消息可能 10 字也可能 2000 字，工具结果动辄数百 token，12 条的上限在 token 数上毫无一致性。生产做法是把 `render_messages` 的产出真正过 tokenizer 估算，达到模型上下文的一定比例（如 70%）再压缩，保留量也按 token 预算折算——牺牲一点实现简单度，换来上下文占用可控。另一个工程细节是压缩本身有一次 LLM 调用的成本与延迟，所以触发别太灵敏：阈值留足余量、`history_keep_recent` 保证新话题不被卷进摘要。

### `tests/test_storage_summary.py`：怎么测这一层

- `TestStorage` 六连：带 tool 消息的完整往返（`messages` / `summary` / `short_term_memory` 三者逐一相等）；损坏文件（`"{not json"`）降级返回 None；`version: 99` 版本不符同样返回 None；文件不存在返回 None；`delete_session` 幂等；保存后目录里不残留 `.tmp`。全部用 pytest 的 `tmp_path` fixture，不碰真实会话文件。
- `TestSummarizer` 两条：`render_transcript` 的输出包含"用户：查预约"与工具名 `query_appointment`，且超长工具结果（`"结果" * 300`）被 `max_tool_chars=50` 截断后单行不超 80 字符；`summarize` 用 `MockLLMClient` 离线跑通，输出以"（摘要）"开头。渲染与摘要拆开测——前者是纯函数断言，后者验证抽象依赖的可替换性。

### 会话的完整生命周期（`app/agent/base.py`）

- **加载**：`BaseAgentRuntime.__init__` 末尾 `load_session(self.session_path)`，拿到数据就恢复 `summary` 与 `raw_messages`，再经 `_restore_extra` 钩子还原短期记忆；拿不到（新建/损坏/版本不符）就全空——重启进程 = 无缝续聊。
- **每轮收尾**：`finish_turn` 固定四步——追加 assistant(JSON) 消息 → `update_short_term(最近6条)` → `maybe_compress()` → `save()`。顺序有讲究：先更新记忆再压缩再落盘，保证磁盘上的状态永远是"压缩后"的一致状态。
- **重置**：`reset_session` 清空 `raw_messages` / `summary`、`reset_short_term()`、`delete_session()`——内存与磁盘一起干净。
- **关闭**：`close()` 触发 `consolidate_to_long_term(raw_messages, summary)` 把本轮巩固进长期记忆；评估沙箱特意**不调** `close`（那次 LLM 写入既花钱又污染隔离环境，见 `app/evaluation/sandbox.py` 的注释）。
- `main.py` 退出序列与之呼应：`agent.save()` → `agent.close()` → 打印 `tracer.summary()`——先落盘再巩固，巩固失败也不丢会话；中途 Ctrl+C 由 `finish_turn` 每轮都 `save()` 兜底，最多丢最后一轮。

## 知识点与面试考点

- **为什么要 `.tmp` + `os.replace` 而不是直接覆写？** 直接 open(w) 会先截断文件，写一半崩溃就丢整个会话；replace 在同一文件系统上是原子 rename，崩溃一致性免费拿到。
- **会话文件损坏为什么返回 None 而不是抛异常？** 用户要的是"还能聊"，不是栈回溯；降级为新会话是最小伤害路径。
- **SESSION_VERSION 检查的作用？** 前向兼容：升级了存储格式后，老版本文件按"无法识别"处理，恢复逻辑不会误读旧结构。
- **摘要为什么必须包含工具调用与结果？** 多轮事实（单号/药品/结论）全在工具消息里；丢摘要等于让模型失忆并诱发重复调用或编造。
- **为什么压缩在回合末尾做？** ReAct 中途重排历史可能拆散 assistant(tool_calls)+tool 的配对；回合边界是安全切面。
- **切点为何避开 tool 消息？** 孤儿 tool 消息违反消息协议，OpenAI 兼容接口会直接拒绝请求；`while` 回退一行就是全部成本。
- **条数阈值的坑？** 消息长度方差极大，条数与 token 数不相关；生产应按 token 预算（如上下文 70%）触发。
- **摘要作为 system 消息注入的好处？** 不占用 user/assistant 轮次结构，模型也不会把它当成用户指令。

## 与 参照的电商客服教学项目 对照与改进

| 方面 | 参照项目 做法 | 本项目做法与理由 |
| --- | --- | --- |
| 摘要函数的依赖 | `summarize(client: OpenAI, model=...)` 直接依赖 openai 客户端，离线不可跑 | `summarize(client: BaseLLMClient)` 依赖抽象，`MockLLMClient` 可跑，测试覆盖到摘要链路 |
| transcript 渲染 | summarizer 内自渲染，混在 summarize 里 | 独立 `render_transcript(messages, max_tool_chars)`，截断长度是参数，可单独断言（`test_render_transcript_includes_tools`） |
| load 校验 | 只检查 `"messages" in data`，不校验 version | `version == SESSION_VERSION` 且 `messages` 是 list，格式演进不误恢复 |
| 损坏降级反馈 | `print` 警告后返回 None | 静默返回 None：库函数不抢占 IO，展示交给调用方 |
| 压缩逻辑位置 | `参照项目的单Agent类._compress_history`，orchestrator 再复制一份（改一处漏一处） | `BaseAgentRuntime.compress_history` 全系统唯一实现，单 Agent 与编排器共用 |
| 切点避开 tool 消息 | 同样有 `while ... role == "tool": split -= 1` 回退（正确做法两边一致） | 相同逻辑，且在注释中写明"孤儿 tool 消息会破坏协议"，教学上讲透原因 |
| 阈值参数 | `history_threshold=10` / `keep_recent=3`，无说明 | `12` / `4`，settings 注释明确"生产应按 token 预算"，简化被显式承认 |

1. **制造损坏文件**：往 `session.json` 写入 `"{not json"` 后启动 `main.py`，确认程序当新会话正常聊天；再写入 `{"version": 99, "messages": []}` 验证版本不符同样降级（对照 `tests/test_storage_summary.py::TestStorage`）。
